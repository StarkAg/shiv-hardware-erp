# Shiv Panel ERP audit — 8 October 2026

Reviewed revision: `df36062`, with the pre-existing local `CounterLayout.tsx` edit left untouched. Scope: the main ERP (`src/main.tsx`) and the backend paths it uses. Companion websites and the separate counter entry point are excluded.

The most urgent problems are accounting changes caused by reopening vouchers, failed-posting data reaching shared bill storage, and missing server authorization. The application builds, but a successful build does not establish accounting correctness.

## Confirmed findings, in recommended fix order

### 1. Critical — Financial APIs accept anonymous reads and writes

**Evidence:** isolated mutation/query reproduction and the dashboard loading without sign-in. `billLedger.postBill`, `bills.get` and `masters.all` do not authenticate the caller. A PIN protects selected destructive operations, not ordinary reading and posting.

**Impact:** knowing the deployment endpoint is enough to call ordinary financial operations. A browser-only read-only screen does not enforce read-only access. The API URL is a client configuration value, not an access credential.

**Fix:** add staff identities and enforce permissions inside each server function, including read access to party/contact data. Keep PIN checks as an additional guard where appropriate. This absence is acknowledged in existing documentation; it is still present in this revision.

**Source:** [posting entry point](../convex/billLedger.ts#L206), [bill query](../convex/bills.ts#L70), [account master query](../convex/masters.ts#L45).

### 2. High — Reopening a ledger-only voucher changes cash and discounts

**Reproduction:** create a standalone cash receipt for 1,000; obtain `vouchers.detail`; rebuild and save using the editor's mapping. The debit moves from Cash to Bank because `emptyBill()` defaults to UPI and the loader never restores the original mode. Separately, a receipt of 900 money plus 100 discount reopens as 1,000 money with zero discount; saving removes the discount entry and puts all 1,000 into Bank.

**Impact:** an apparently unchanged save changes the books. This affects the `/bills/voucher/:voucherId` path, not ordinary bill snapshots that already retain these fields.

**Fix:** return and hydrate the original money account, actual money amount and discount split. Preserve all existing posting details unless explicitly changed. Test unchanged round trips for each supported voucher kind.

**Source:** [voucher detail](../convex/vouchers.ts#L397), [editor hydration](../src/features/bills/BillBuilder.tsx#L2567), [UPI default](../src/lib/types.ts#L261). Two isolated reproductions confirmed this.

### 3. High — Reload uploads failed postings and can split a bill from its accounts

The normal debounced push excludes `postError` bills, but the three-second startup push sends **all** bills. The backend snapshot endpoint accepts those records without updating voucher entries.

**Reproduction:** post a bill for 1,000. Simulate a failed local edit to 2,000 with a newer timestamp and `postError`. Send that snapshot through the endpoint used at startup. Shared bill storage becomes 2,000 while the voucher remains 1,000. A brand-new failed bill can likewise enter shared storage with no voucher at all.

**Fix:** apply the failed-posting exclusion at every client entry point and reject invalid snapshot updates server-side. Financial bill fields should change through the atomic posting command, not an unrestricted snapshot writer.

**Source:** [startup push](../src/main.tsx#L68), [normal filtered push](../src/lib/store.ts#L25), [snapshot acceptance](../convex/bills.ts#L26). Two isolated reproductions confirmed this.

### 4. High — Soft locks and stale edits are not enforced when posting

`postBill` accepts no lock owner or expected revision and replaces existing voucher lines. A device can hold a stale draft, lose its heartbeat, allow another counter to save, then submit the stale draft before its next heartbeat tells it the lock is held elsewhere. Two tabs in one browser also share the same device ID.

**Reproduction:** claim the bill for counter A; verify counter B's lock claim is refused. Update the bill to 2,000, then submit the earlier 1,000 snapshot. Posting accepts it and the voucher returns to 1,000.

**Fix:** atomically compare the expected server revision and lock token during posting. On mismatch, preserve the operator's draft and show the newer record. Client-clock timestamps are not a substitute for a server revision.

**Source:** [soft lock](../convex/billLocks.ts#L16), [posting arguments](../convex/billLedger.ts#L206), [replacement of existing voucher](../convex/billLedger.ts#L448), [browser identity](../src/lib/device.ts#L13). Confirmed by isolated test; the network timing scenario is inferred from these paths.

### 5. High — A stale catalog snapshot replaces newer rates

**Reproduction:** save an item at 200, then submit an older nonempty snapshot containing 100. The stored rate becomes 100. `catalog.save` replaces the whole row and has no version check. The empty-catalog guard does not protect stale nonempty data.

**Impact:** a delayed startup push or overlapping edits from two counters can revert prices or remove newly added catalog entries. General store persistence schedules catalog uploads even when the action was saving a bill.

**Fix:** use item-level mutations with revision checks; hydrate before any startup upload and send only deliberate catalog changes. Show failures rather than swallowing them.

**Source:** [catalog replacement](../convex/catalog.ts#L103), [startup upload](../src/main.tsx#L72), [all-store persistence](../src/lib/store.ts#L201). Isolated overwrite reproduction passed; actual two-device network timing was not exercised.

### 6. High — Changing a voucher date across April keeps the old financial year

**Reproduction:** post on 31 March 2026, reopen and change to 1 April 2026 without changing voucher type. The voucher date changes, but `fy` stays `2025-26`; `fyOf(newDate)` is `2026-27`.

**Cause:** the update assigns a new `fy` and number only when the voucher type changes.

**Fix:** treat a financial-year change as a series change too, or explicitly reject cross-year edits. Update the date, year, number and any linked settlement consistently.

**Source:** [conditional numbering/year update](../convex/billLedger.ts#L458). Confirmed by isolated reproduction.

### 7. High — Profit includes sales that failed to post

**Reproduction:** give an item a purchase cost of 600 and a local sale of 1,000 marked `postError`. `profitLines` and `totalsOf` still report 400 profit.

**Impact:** the Profit screen can show earnings from a sale that the ledger rejected. Unposted purchases are also eligible to enter the cost book. Because this page uses the local store, figures can differ between devices.

**Fix:** exclude failed postings from both sale lines and purchase-cost inputs, while showing their excluded count/value separately. Use one agreed source of posted records for accounting reports.

**Source:** [profit input](../src/features/profit/Profit.tsx#L158), [cost book](../src/lib/profit.ts#L140), [sale selection](../src/lib/profit.ts#L288). Isolated sale reproduction confirmed.

### 8. Medium — Lump-sum sales disappear even from Profit's missing-cost list

**Reproduction:** a sale containing a single `Bill` line for 12,000 produces zero profit rows. The intended `lump` handling is never reached: `billLines` has already removed `Bill` as an amount-only charge.

**Impact:** users cannot see that these sales were excluded or need costing. The existing test `a bill entered as one amount has no item to cost` fails on this exact behavior.

**Fix:** separate lump-sum goods from fees/tax/discount lines before filtering, and explicitly represent uncosted sales in report coverage.

**Source:** [amount-only names and line filter](../src/lib/types.ts#L365), [unreachable lump handling](../src/lib/profit.ts#L295). Existing failing test and isolated reproduction agree.

### 9. Medium — Converting a quotation keeps its Q-number as the sale number

**Reproduction:** save quotation `Q-1`; convert it with a requested bill number `2` and `fromQuote: Q-1`. Posting returns number `Q-1` and voucher reference `BILL-Q-1`.

**Cause:** `billNumberFor` unconditionally returns the already stored number for the same ID, even when that stored record is a quotation. The frontend's conversion assigns a bill number, but the server replaces it with the old quotation number.

**Fix:** distinguish same-document retries from quotation-to-sale transitions. Allocate a bill-series number on conversion and keep the original quotation reference separately.

**Source:** [number reuse](../convex/billLedger.ts#L105), [conversion](../src/features/bills/BillBuilder.tsx#L3387). Confirmed by isolated reproduction.

### 10. Medium — The ERP still offers cash-posting actions that cannot succeed

The deliberate cash/book separation is not itself a defect. The unfinished adaptation of the ERP is: Home still links to Cash Pending, which offers account assignment and `Post what can post`. Assignment requires a voucher to exist after calling `postCashEntry`, but that helper immediately returns with posting disabled.

**Evidence:** Home displayed 177 waiting notes during the read-only review. Synthetic assignment fails with `The books did not take this note`. Bill Flow receipt/payment conversion has the same dependency and an existing failing test reports `Assign this cash entry to a party account before converting it` even after an account is chosen.

**Fix:** remove or redesign ERP workflows that assume cash notes post to the books. Preserve the intentional separation; do not turn posting back on merely to make old tests pass.

**Source:** [intentional switch](../convex/cash.ts#L26), [assignment](../convex/cash.ts#L591), [Cash Pending buttons](../src/features/cash/CashPending.tsx#L56), [Bill Flow conversion](../convex/billFlow.ts#L84).

### 11. Medium — Sidebar navigation silently loses unsaved input

**Browser reproduction:** open Receipt, type synthetic party `ERP Audit Unsaved` and amount `123`, then click Home. No leave warning appears. Reopen Receipt: the party is blank and the amount is zero.

The Cancel handler has a warning for a new unsaved bill, but sidebar navigation bypasses it. Existing-record edits are not covered by its `!bills.find(...)` condition either. No autosave is intended here, so preventing accidental loss needs an explicit navigation guard.

**Fix:** compare against the initial document, block route changes while dirty, and handle tab close/reload. Keep discard and save as explicit choices without creating a posted draft.

**Source:** [Cancel-only check](../src/features/bills/BillBuilder.tsx#L3396), [sidebar links](../src/components/AppLayout.tsx#L293). Confirmed in Safari; no synthetic financial record was saved.

### 12. Medium — Error recovery's Home button opens another missing page

**Browser reproduction:** open `#/qa-missing-page`, then click the central Home button. The address becomes `#/quote-options` and the same “This page has moved” screen remains. Both NotFound and AppError use this removed route; the main router's home is `/home`.

**Fix:** send both recovery buttons to `/home`, and maintain explicit redirects for older supported links.

**Source:** [NotFound](../src/components/RouteFallbacks.tsx#L32), [AppError](../src/components/RouteFallbacks.tsx#L72), [router](../src/main.tsx#L166). NotFound reproduced in Safari; AppError has the same destination in source.

### 13. Medium — New bills use yesterday's date before 05:30 in India

`today()` uses `new Date().toISOString().slice(0, 10)`, which takes the UTC calendar date. At 02:00 on 8 October in India, that expression returns `2026-10-07`.

**Impact:** early-morning entries and quotation conversions receive the preceding date by default, affecting daily totals and potentially the year boundary.

**Fix:** use one Asia/Kolkata business-date helper everywhere, including conversions, filters and report defaults. Add midnight and 1 April boundary cases.

**Source:** [builder date helper](../src/features/bills/BillBuilder.tsx#L262). Reproduced with a fixed `+05:30` timestamp; no device clock was changed.

### 14. Medium — “Kept on this PC” can be false when storage fails

`localAdapter.save` catches and ignores storage exceptions. After posting fails, `postStored` saves locally and tells the operator the bill was kept. If localStorage is full or unavailable, the data only remains in memory and disappears on reload.

**Fix:** propagate persistence failure to the caller, give an explicit error and preserve an export/retry path. IndexedDB and bounded caches would reduce the chance of exhausting the shared storage budget.

**Source:** [swallowed storage failure](../src/lib/db/adapter.ts#L52), [failed-posting message](../src/features/bills/BillBuilder.tsx#L3088). A simulated quota failure confirmed that the adapter reports no error; an actual full-browser-storage run was not performed.

### 15. Low — Collapsed sidebar retains shortcut labels and crowds its icons

**Browser evidence:** after collapsing, F-key labels remain; longer `Alt+F...` labels crowd/shrink the corresponding icons. The rail uses fixed narrow link widths, while keyboard labels explicitly retain an 11px font and the label span remains a flex item.

**Fix:** render only nonshrinking icons in the collapsed rail. Move the label and shortcut into the accessible name/tooltip, and test every menu item at the collapsed width.

**Source:** [label and key rendering](../src/components/AppLayout.tsx#L299), [collapsed rail classes](../src/components/AppLayout.tsx#L369). Visually observed in Safari. No claim is made about mobile layout from this desktop test.

## Improvements worth scheduling

- **Restore pinch zoom.** The viewport disables user scaling and global touch handlers prevent multi-touch zoom. This makes small accounting tables harder to read for users who need magnification. See [viewport](../index.html#L7) and [gesture handling](../src/main.tsx#L40). Source review only; physical mobile testing remains outstanding.
- **Reduce whole-dataset synchronization.** `ConvexSync` subscribes to every bill; snapshot saves read all bills plus deletion markers; the dashboard scans all vouchers and entries. This creates increasing network, browser-storage and backend work as history grows. Introduce incremental changes, indexed period queries and pagination. This is a scaling concern, not a measured production outage.
- **Split expensive frontend modules.** The production build reports a 715.01 kB main JS chunk before compression and warns that static PDF imports defeat the dynamic import. Lazy-load routes and PDF/print tools. Bundle sizes are measured; no slow-network timing claim is made.
- **Avoid treating a partial month as a finished month in forecasts.** Dashboard includes the current month and `project()` feeds the last six raw monthly totals into its fit. Early-month sales are therefore compared with full months. Use completed months or an explicitly labelled month-to-date adjustment. See [series construction](../convex/reports.ts#L717) and [projection](../src/features/home/Charts.tsx#L249).
- **Protect completed accounting periods.** The reviewed posting path has no common financial-period lock. Add an explicit owner-controlled correction policy before relying on closed-period figures. This is a capability gap, not evidence that past records were altered.
- **Test realistic workflows, not just helpers.** Add browser coverage for unchanged voucher round trips, dirty navigation, quotation conversion, lock loss, failed-save reload and recovery routes. Align tests/documentation with the deliberate cash separation.
